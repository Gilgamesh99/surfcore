## 现象与根因

更新页顶部显示“已是最新”，SurfCore 行却显示“本地有未提交改动”，详情又是“原因不明”。生产 main 的 28 个未提交路径包含已部署的 QQ 续聊、受控生图、B 站全天监听及必要兼容修复；三个功能工作树保留各自的测试与文档，部分尚未汇总。大量 CRLF/LF 差异放大了实际补丁。

旧检查器把本地 ahead 与 dirty 一律阻断，而更新应用只允许 ff-only：仅提交本地改动能解除 dirty，但未来远端前进后仍会分叉失败。顶部徽标使用提醒队列 pendingCount，无法区分没有更新、被暂缓提醒、受阻和检查失败。Git 排队使用不存在的 report.latest，退出后的 helper 又把 Git SHA 按 package version 校验，缺少固定目标与排队后状态复查。

## 完整逻辑

1. **链路**：DSH 宿主中 SurfCore 的 updates.js 检查 Git；client.js 展示全部检查结果并提交选中项。Git 更新排队写入独立 helper 事务，apply-update.mjs 等宿主退出后再动仓库。QQ MCP/bridge 和 B 站 scheduler 继续使用生产目录中的既有功能代码；本次同时补入各自测试和 case。
2. **机制**：检查确认实际分支、仓库根、远端、HEAD、工作区及 Git 操作状态；fetch 失败不把缓存 origin/main 说成最新。SurfCore 允许已提交的本地改动，其他组件默认 ff-only。更新固定 fromHead/targetSha/分支/策略，helper 重新核对并建立备份引用。能够快进则快进；分叉则普通合并，保留两边历史。发生冲突停止并中止本次合并，报告路径和恢复结果；不会自动选择一侧覆盖功能。
3. **影响面**：宿主更新服务、退出后 helper、更新页面三个读者。远端只 fetch，不 push。用户配置、密钥、会话、图片额度账本及通知水位不作为代码提交。离线测试使用临时 Git 仓库和本地远端，不产生 QQ 消息、B 站互动或付费生图。未来成功更新可能改变远端代码行为，仍需正常回归。
4. **取舍**：只提交现有文件成本最低，但遇到远端分叉仍不可更新；自动 stash/rebase/覆盖会隐藏冲突或改写本地历史，不采用。本次选择已提交定制 + 固定目标 + 可中止 merge，代价是发生实际冲突时需要人工解决。当前远端和基线相同，先把已部署功能及配套测试落入 main；不为消除 ahead 而丢弃本地提交。
5. **生效与重启**：更新后端需要重载 SurfCore 主插件；页面需要刷新资源。真实后续 Git 应用继续等待宿主退出，避免覆盖运行中的插件。QQ/B 站功能代码来自现有部署，不靠保存统一设置刷新，避免重置通知水位。当前生产加载证据见验收记录。
6. **验证**：运行 npm run test:audit、npm run test:regressions 和插件 npm test。更新器临时 Git 场景覆盖快进、无冲突分叉、本地提交保留、冲突恢复、排队后 HEAD/分支/工作区变化、固定 SHA、忽略文件碰撞、网络失败及排队失败。UI 断言覆盖受阻/失败/未检查/暂缓提醒/同版本新 SHA 和 pending restart 的选择权限。结果见验收记录。
7. **回滚与残余**：整合前四个工作树的补丁、未跟踪文件和哈希清单保存在 D:/ProgramData/DSH NEXT/Soul/backups/surfcore-main-integration-20261112，私有配置备份不进入版本库。未来每次 Git 更新先保存 backupRef；Git 不使用 ZIP 文件复制回滚，界面明确给出人工恢复指引。优先在停宿主、确认工作区后用反向提交恢复需要撤销的代码，保留最新 state 与配置。普通 Git 合并只能保证历史与文本保留，不能保证未知未来代码的语义兼容；冲突时会停下。
