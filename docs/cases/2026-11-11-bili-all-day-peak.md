# B 站全天评论/@监听被峰时顺延阻断

日期：2026-11-11（Asia/Shanghai）
分支：`hotfix/bili-all-day-20261111`，基线 `0ce8580`。

## 现象与根因

用户已经开启「全天倾听」，17:12 和 17:31 的两条 @ 已进入 B 站通知，但专用模型会话没有启动。配置、登录和 token 预算正常。`listenTick()` 在读取 `listen.allDay` 前先执行 `peakBlockedNow('评论区倾听')`，工作日 14:00–18:00 直接返回。全天开关原本只放开生物钟窗口，无法放开更早执行的峰时闸门。

18:00:46 原代码自然离开峰时后捕获两条通知；18:09 模型将两条视频的感想合在第二条 @ 下回复。因此这次问题属于监听调度，不属于 FFmpeg、视频索引或评论发布失败。此自然恢复不能作为补丁生效证据。

## 完整逻辑

1. 链路：DSH 宿主加载 SurfCore 主插件，`plugins/surfcore/lib/index.js` 启动 `scheduler.js`；监听器 GET B 站 reply/at 通知，经互动/预算/间隔/时间窗口筛选，将提示排入专用会话，再推进角色目录下 `whale-listen.json`。模型会话随后分析内容、按现有工具规则回复。UI 的 `client.js` 展示全天倾听说明。
2. 机制：已收到的评论/@属于被动互动。开启全天倾听后，该路径跳过峰时顺延；关闭时仍遵守峰时和生物钟窗口。互动开关、评论开关、token 预算及投递前预算复查、轮询间隔、owner 范围和通知水位继续生效。
3. 影响面：一个宿主中的 B 站评论/@监听分支及一处设置说明。峰时内的新评论可能产生正常模型费用，预算仍约束费用；自主浏览、动态、私信、直播没有放开。没有修改账号、密钥、用户配置或通知水位。
4. 取舍：全局关闭峰时顺延会同时放开自主后台任务，且 QQ 设置与 B 站读取的统一配置存在不一致；本次选择仅由已有 `allDay` 控制被动评论/@。改动小，可独立回退，不依赖增加新设置。
5. 生效：仅复制源码不等于旧进程已加载；只停启 B 站 scheduler 也会复用静态导入。部署后需重载 SurfCore 主插件并检查新策略日志。不要保存统一设置作为重载手段，因为 `invalidate()` 会清空监听水位，可能漏掉待处理通知。
6. 验证：真实导出的 `startScheduler().listenTick()` 在隔离目录、假时钟与假通知下运行。固定周三 17:15，验证全天在峰时且窗口外仍投递、非全天峰时继续阻断、互动/评论/预算限制、轮询去重、首次基线、原有窗口和自主任务避峰。测试禁止外部网络、子进程及非夹具数据访问。
7. 回滚与残余：恢复备份的 scheduler/client 后重载同一插件，保留最新通知水位，切勿恢复旧水位重放消息。本次没有修复「保存设置重置水位」、QQ/统一配置成本字段来源差异、模型合并多条回复的选择或原有 300 秒轮询延迟。

## 改动

- `plugins/surfcore/lib/scheduler.js`：先读取评论监听配置，再用 `!listenerCfg.allDay` 限定峰时闸门；增加启动策略日志，供运行时确认。
- `plugins/surfcore/lib/client.js`：全天倾听帮助文案明确峰时豁免和预算/互动限制。
- `plugins/surfcore/scripts/test-bili-all-day-listener.mjs`：真实调度器离线行为回归。
- `docs/HANDOFF.md`、`docs/PITFALLS.md`、`docs/COORDINATION.md`：交接、原因与协作登记。

## 失败可见性

本补丁不新增远程 API 或错误分支。原有预算/互动阻断保持；设置说明明确这些限制，启动策略日志用于判断加载状态。离线测试断言被阻断时不请求通知、不投递并保留水位；预算在投递前耗尽也不得推进水位。若尚无新策略日志，不得宣称运行时已经修复。通用「峰时原因只在日志中」的界面提示缺口仍是残余，不在本次窄修范围。
